# 第 25 章　接下来可以做什么

[中文目录](../README.md) · [英文原章](https://sdiehl.github.io/write-you-a-haskell/ch25-future-work.html) · [原文源码](https://github.com/sdiehl/write-you-a-haskell/blob/51c70f804173c9d013187c543a353686b413ad50/book/src/ch25-future-work.md)

最早我们只有一个计算器。现在，Fun 能推断类型，有代数数据类型、记录和类型类，还能编译出直接在机器上跑的程序。一路走来，我们甚至给它写了优化器和垃圾回收器。

接下来，就轮到你决定这门语言要往哪里走了。它的每个设计决定落在什么地方，你已经有个概念。想试试另一种做法，还可以退回到更小、更容易看懂的章节快照，从那里分岔。下面几条路都值得一试。

## 给 Fun 加上你想要的能力

### 把「先别算」写进程序

有时我们确实想先把一项计算描述好，等到需要结果时再执行。我会从**显式延迟**着手，借用 call-by-push-value（CBPV）的思路，在语言里区分「一个值」和「一项计算」[^levy2001]。这样读代码时就能看见，哪一步把计算挂起来，哪一步要求它交出结果。

还有一个独立的选择：同一项计算被要求交出两次结果，要不要再算一次？如果想实现按需调用（call-by-need），就得记住某个挂起的计算已经求过值，让后来的使用者共享结果。还得想好，正在求它的值时，如果它又递归地要求自己的值，该怎么办。已有的闭包表示能帮我们保存计算所需的环境，但加一种 thunk 对象只是开头。可以设计一层类似 STG 的中间语言，专门表达挂起、强制求值和更新这些操作。

### 模块和分离编译

程序一长，迟早会有人不愿意再把所有东西塞在同一个文件里。模块可以把相关定义放在一起，只公开接口里列出的部分。分离编译再往前走一步，让你只重编有改动的部分，省下每次重编整个程序的时间。

在一次编译之内，我们已经能给每个绑定分配独一无二的名字。拆开编译之后，哪些名字的身份必须保持稳定？哪些类型信息得随接口保存，让下一次编译还能认出来？类型类让问题更有意思：导入的函数可能依赖实例，得明确规定它能看见哪些实例。动手时不妨从一套要求显式写出接口的小模块系统开始。

### 行多态、效应与类型类

Fun 目前的记录有自己的类型名，字段也固定。如果我只想写一个取 `x` 的函数，它能不能接受**任何含有 `x` 字段的记录**，其余字段随你加？**行多态**（row polymorphism）就能表达这种要求。这里的「行」可以理解成一组字段，把它未知的剩余部分留作参数。类似的思路还能用来描述效应，用**效应行**（effect row）在类型里列出一项计算可能产生的效应。

要做到这些，现有的约束语言还得扩充。但动手的方法和前面一样：先找一个你想写、现在却写不了的小程序，写出你希望它拥有的类型，再推敲推断器需要知道什么才能得到这个类型。

也可以研究多参数类型类、函数依赖，或者类型族。我们沿用了 Haskell 98 的一些限制，实例搜索才维持在一个容易掌控的范围内[^haskell2010]。一次只放宽一条。这样，当搜索出现歧义或更难终止时，你就有机会看清，原来是哪条限制帮了忙。

### 让未知目标的尾调用也不长栈

已知要调用哪个函数时，Fun 已经能使用 LLVM 的尾调用约定。目标要等到运行时才知道时，就得经过 C ABI 的运行时调用路径，一长串调用仍可能积累栈帧。还可以把这处缺口补上。

一种做法是连 apply 的分派也放到 LLVM 里生成。实参数量刚好、进入部分应用对象（PAP）、实参给多了，这三条路径就有机会采用同一套尾调用交接约定。最值得琢磨的是给多了的时候：得先用前几个实参调用函数，等它返回另一个函数，再把剩余实参交过去。等第一个结果的这段时间，多出来的实参存在哪里？可以从第 19 章的 eval/apply 模型出发推演[^marlow2004]。

### 特化与未装箱值

现在，算术运算的中间结果已经可以直接放在原生寄存器里。可一旦跨函数调用，各种参数仍统一按一个带标签的机器字传递。如果编译器在某个调用点知道了具体类型，它就有机会替这个调用生成一个**特化版本**，直接传未装箱的参数。如果连类型类字典也确定了，原本要从字典中挑方法的地方还可以改为直接调用。

值得试，但多生成一份特化函数，就要多花一份代码空间。不妨先拿一个很小的数值函数开刀，看看机器码实际省了哪些工作，可执行文件又长大了多少。这两个数都量过，再考虑把实验推广成通用的特化器。

### 优化与调试

把函数体内联到调用处，可能露出此前看不见的常量、构造器，或者字典里的具体方法，下一遍优化便能继续化简。也可能因为同一段计算被复制了几份，运行时反倒多做了活。第 23 章的执行轨迹和抽象机步数正好可以拿来检验。挑一个真能跑的程序，看看它具体从这项优化里得到了什么。

另一个可以独立尝试的项目是源码调试器：底下跑的是原生可执行文件，屏幕上却能逐行单步执行 Fun 源码。DWARF 调试信息可以把机器指令对应回源码位置。若还想在停下时查看变量，就得告诉调试器变量在哪个作用域里、值现在存在哪里。起步时先关掉优化。等这个版本可用了，再来琢磨怎么向读者解释，一个被优化器删掉的变量究竟「去了哪里」。

## 从编译器的哪一层动手

不必为了试一个点子，把整个编译器重写一遍。选择你最想解决的问题，直接回到相关的那层。

| 想尝试的方向 | 第一个值得看的地方 |
| --- | --- |
| 显式延迟 | Core 的求值规则，以及进入闭包时执行的代码 |
| 模块 | 名称解析后分配的唯一身份，以及每个编译单元需要保存的元数据 |
| 行多态或效应 | 类型、约束，以及如何翻译成显式的中间语言（elaboration） |
| 类型类扩展 | 实例检查与约束求解 |
| 未知目标的尾调用优化 | Flat 里的调用、慢速入口，以及运行时的 apply |
| 特化 | 擦除前保留的类型证据，以及函数调用约定 |
| 源码调试 | 源码区间怎样一路传到 Flat，再交给 LLVM 生成代码 |

查某种中间表示的细节时，可以翻[附录 C · 中间表示（英文）](https://sdiehl.github.io/write-you-a-haskell/appendix-c-ir.html)。想确认编译器和运行时之间怎么传值、怎么调用，可以翻[附录 D · 运行时 ABI（英文）](https://sdiehl.github.io/write-you-a-haskell/appendix-d-runtime.html)。

恭喜你走到了这里！现在，把一行源码变成能在机器上跑的程序，中间要经过哪些步骤，你已经亲自走过了一遍。希望当初看起来高深莫测的某个部件，到这里已经变成了「给我一点时间，我也能坐下来把它写出来」。

从 Haskell 2010 至今，函数式编程又往前走了很远。这本书只触到了其中的一部分。语言设计、类型系统、编译器实现，每个方向都还有值得亲手验证的想法。挑一个最让你好奇的，打开对应的章节快照，试试看会发生什么。
